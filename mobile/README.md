# Butter mobile — development client (#447–#451)

Independent Android/iOS Flutter app: configure **one** Butter address → password or OAuth sign-in → choose Workspace → paginated authorized Agent list. Workspace/member management, self-service profile/avatar/password, appearance settings, Model Providers and LLM/Loop/Sequential/Parallel/Workflow Agent configuration are available too. This is not the complete Flutter product. There are no global administration, Skills management or server-list screens.

## Develop

Pinned toolchain: **Flutter 3.38.9 / Dart 3.10.8**, **Buf 1.71.0**, Go from the root `go.mod` (only for the server contract fixture). Install Android SDK/JDK 17 for Android, or Xcode/CocoaPods on macOS for iOS. Existing Go/Web builds do **not** depend on Flutter.

```sh
cd mobile
flutter pub get --enforce-lockfile
flutter run                     # choose Android/iOS; enter address in the App
bash tool/check.sh format
bash tool/check.sh analyze
bash tool/check.sh test
bash tool/check.sh contract      # production Go services on a disposable loopback server
bash tool/generate.sh --check    # regenerate into a temp tree and detect drift
flutter build apk --debug
# macOS only:
flutter build ios --simulator --debug --no-codesign
```

`bash tool/generate.sh` regenerates `lib/gen/` from the root proto schema and locked Buf dependencies. Dart protobuf and Connect generators are resolved from `pubspec.lock`; neither gRPC stubs nor hand-authored wire models are used. Commit generated output; do not hand-edit or reformat it. `.github/workflows/mobile.yml` separately checks format, analysis, tests/contracts, generation drift and both native builds.

## Protocol decisions and evidence

- `connectrpc 2.0.0`, `protobuf 6.1.0`, `protoc_plugin 25.1.0`; native `dart:io` HTTP/1.1, **Connect binary unary**, `application/proto`, `/api/agents.v1.Service/Method`. Not gRPC. No JSON adapter was necessary.
- `tool/contractserver` registers production Connect handlers with `connectx.HandlerOptions()`, real application Login/Me/Logout/ListWorkspaces/ListAgents, real auth/Workspace middleware and `/ping`. Only database persistence is replaced by ephemeral repositories. `test/contract_test.dart` calls those handlers from Dart, including invalid password, unauthorized Workspace and revocation, both at root and at a reverse-proxy `/butter` prefix. It proves actual backend protocol interoperability, not deployment/device acceptance. The fixture cannot bind non-loopback addresses and never executes an Agent. `tool/contractserver/workflow_runtime_test.go` (`go test ./mobile/tool/contractserver/`) is the exception for #452: it saves Workflows shaped like the editor's output through those same handlers, reads the stored records back, and runs them on the production runner against a fake OpenAI backend. It asserts that a Router takes its route or default edge, that a fan-out reaches the Join with every branch, that a Parallel Worker runs once per list item, and that a Human Input node pauses with its question and form and resumes into its successor; it also asserts that the server refuses the graphs the editor flags. It does not render the form in the App (separate ticket).
- Address verification calls `/ping` **and** the generated, public `ListOAuthProviders` RPC without credentials. The second check distinguishes a Butter RPC endpoint from an arbitrary web page. Auth/Workspace requests carry no Workspace header; Agent requests carry the selected `X-Workspace-ID`.
- HTTPS is default, normal OS/Dart certificate validation stays enabled, redirects are refused, userinfo/query/fragment and dot paths are rejected. A deployment prefix is supported; enter the public root/prefix, not `/api`. Proxies must serve `/ping` and Connect beneath that prefix without redirects.
- Generated protobuf messages remain intact in memory: optional absence/explicit zero and unknown fields survive list decoding. Agent editing (#451) copies the complete generated message and changes only edited fields; tests cover optional/int64, nested unknown fields and future enum retention. Unknown type/lifecycle and legacy embedded children block editing; unknown Include Contents/ContextGuard strategy is shown as retained and has no rewriting control. Server validation still wins.
- One request scope is disposable. Switching server, account or Workspace closes its HTTP client and increments a generation. Late responses cannot restore old identities or lists. Secure-store writes/deletes are serialized, including writes that outlive a cancelled login. Entering the background closes observation/request scope; foreground recovery performs reads only, never repeats Login or side effects.
- No automatic retries, refresh tokens, root/API-token login or persistent Agent cache. 401/Unauthenticated clears sensitive state and secure credentials; 403 remains a permission error. Logout clears locally first and explicitly reports unconfirmed remote revocation. Storage failures remain visible and fail closed; if the OS refuses deletion, the app cannot honestly promise that the OS record was erased.

## OAuth sign-in (#448)

The provider only ever returns to the server's one configured `redirect_url`, which is a web page, so the App cannot be the callback and `BeginOAuthFlow.redirect_uri` is not honored. The App uses a PKCE-bound one-time handoff (`docs/api.md` § Native App sign-in): `BeginOAuthFlow(native{return_uri, code_challenge})` → system browser (`url_launcher`, external application; only `http(s)` URLs are opened) → the web callback page → `ee.orz.butter:/oauth/callback?handoff=…&state=…` → `RedeemOAuthHandoff(…, code_verifier)`. The session token never appears in a URL; the handoff is single-use, expires in 2 minutes and is useless without the verifier that never left the App.

- The pending flow (server, provider, state, verifier, start time) lives in secure storage so it survives the OS killing the App during the browser leg, and expires after 10 minutes. Cancel, a timeout, a stray link with another state or path, a duplicate callback and a late response from a replaced flow all leave the user signed out with a clear message and never repeat a side-effecting call.
- Links arrive through `app_links` (its stream includes the cold-start link). Flutter's own deep-link routing is disabled in the Android manifest and iOS `Info.plist`, so the scheme reaches only this handler.
- **Operator step:** the server must list the return URI in `auth.native_return_uris` (exact match). The default is empty, which disables native sign-in; the App then reports that this server does not support it. `ee.orz.butter` is a **development** scheme, not an approved release identifier. A custom scheme can be claimed by another installed app, which is why PKCE binds redemption to this App instance; choose the release scheme (or verified App/Universal Links) with the other release decisions above.
- Not exercised here: iOS builds and real-device browser round trips (this Linux environment has neither). The Go↔Dart contract test (`test/native_oauth_contract_test.dart`) drives the real handlers with a fake provider only.

## Credential boundary

`flutter_secure_storage 10.0.0`: Android Keystore-backed encrypted storage; iOS Keychain with `first_unlock_this_device` (not migratable to another device), Keychain entitlements in every app build configuration. Android application backup/transfer is disabled. Only the server address and non-sensitive device appearance settings are in ordinary preferences. The secure record contains its server binding and token; a mismatched server record is deleted before any authorized request. Passwords are never persisted, printed or placed in URLs, and the password field is cleared on submission. No shared server/account session pool exists.

Changing the address requires confirmation, closes the old scope and clears credentials/cache **before** verifying the new address. This does not call Stop or revoke the old server's Detached Run. Future run observers must live under the same context lifetime.

## Model providers (#450)

| Web operation | API/storage | App entry | Tests |
| --- | --- | --- | --- |
| List / view providers | ModelProviderService List/Get, `X-Workspace-ID` | Agents page → Model providers | `model_provider_context_test`, `model_provider_widget_test`, real `model_provider_contract_test` |
| Create / edit (type, base URL, API key, models with ID, alias, context window) | Create / Update (the whole object is replaced) | Add provider, Edit provider | `provider_draft_test`, widget and contract tests |
| Delete | Delete, after a confirmation naming the provider | Provider details | same tests, plus `mobile/tool/contractserver/main_test.go` |
| Refused change because Telegram Destinations use an alias | `FailedPrecondition` with the alias and Destination IDs | Shown on the form or the delete dialog | contract tests against the real `TelegramReferenceGuard` |

Any member of the Workspace may use these calls: the server has no owner/admin check here, so the App does not invent one. The provider belongs to the selected Workspace; switching Workspace, account or server drops the list, the detail and unsaved drafts.

**Credentials.** The API exposes no `credential_set`, write-only field or connection test, and returns the key in plain text, so the App does not pretend otherwise. It never displays the key: lists and details show only "API key: Set / Not set", logs and errors do not carry it and drafts are not persisted. Editing offers Keep (default, the stored value is untouched), Replace (an obscured field) and Remove (asks for confirmation). Nothing is auto-retried.

**Model fields.** Model ID is what the provider is called with; Alias is the name Agents and Telegram select; Context window is the **input** capacity in tokens (0 to 4,294,967,295). Empty and 0 both mean unset, and the server then uses its own default. It is not the maximum output tokens, and the provider API has no output-limit field, so the App offers none. (An Agent's `context_guard.max_tokens` is likewise an input-context override, not an output limit.) The form needs at least one model, like the Web page.

**Unchanged fields.** An edit starts from a deep copy of the stored message and each model row keeps its own original, so unedited and unknown protobuf fields survive an update, also when rows are removed or reordered. If a save reply is lost the App reports an unconfirmed outcome and reloads instead of replaying the write.

Limits: key rotation policies and a live connection test do not exist in this ticket. The widget tests include a phone-sized 2× text run with reader labels; that is **not** device accessibility acceptance, and no Android/iOS device or release verification was done for this ticket.

Unbound Agent configuration writes are available to Workspace members under the existing backend rules. The App does not invent an owner-only restriction. The immutable ID is the only lookup/reference key; the display name is never resolved. Runtime name is supplied on create and server-controlled thereafter. Existing type is retained by this editor (type selection is offered on create); changing existing type stays with Web to avoid discarding future type-specific fields. Blocked lifecycle states, unknown types, historical embedded-child configurations and a Pi/Cursor leaf that holds children or Butter-side behavior fields (the server refuses them on write, so a record that has them is legacy) are read-only (composite saves would discard embedded children). Pi and Cursor leaves and ButterBoxes were added by #453 (next section). No deletion, restore, purge or operation-management action is provided for Agents.

Model choices include every configured provider's alias (model ID when no alias is set), keep custom/current values, and never cache or display provider keys. Child choices load every Agent page; choosing an ID does not embed or modify that resource. The server enforces existence, Workspace scope, cycles and single-parent ownership. Existing unavailable references remain visible and can be removed, not silently dropped.

**Advanced fields.** Input/output schema text is validated as JSON on edit; it is stored configuration, not a claim of runtime structured-output support. Labels and metadata have separate key/value rows, not a whole-Agent JSON editor. ContextGuard's Threshold has only an Agent Context Override in input tokens (0 inherits Model Context Capacity); Sliding Window has only its content-entry limit (0 defaults to 20). Neither sets maximum output tokens. Switching a known strategy clears the other strategy's field; leaving it unchanged preserves the message including unknown fields. Known backend ContextGuard errors have specific safe explanations; arbitrary server payloads are not echoed. Existing Skills are selectable/removable by name from the read-only Workspace catalog; missing previously selected names remain until deliberately removed. Unedited MCP/Remote/files/Memory/Card Policy/runtime associations remain intact for their separate tickets.

**Git boundary.** Every explicit save first reads GetWorkspaceRepoBinding; an unavailable read never falls back to a DB-only write. Create includes initial Agent Content. An update uses UpdateAgentConfiguration only once the binding has an Active Revision (`active_commit_sha`), matching backend Git ownership. Bound-but-not-onboarded content remains database-owned and editable by members through UpdateAgent. Git-owned updates carry the original int64 version, the active SHA and only changed description/prompt/global-prompt file actions (empty means DELETE). A response that silently ignores DB-path content changes is treated as unconfirmed, not success. CAS conflicts ask for a reload, never force overwrite. Unbound UpdateAgent does not accept a client-observed version, so the App does not promise stale-editor CAS there. Production-service Dart tests cover unbound CRUD, bound-but-not-onboarded member edits, read-only Skill catalogs and real validators at root and `/butter`; bound routing/version/path mapping is tested at the controllable HTTP boundary. A real Git-bound deployment and operation-recovery/device acceptance are **not** established by these tests.

Drafts live only in memory, warn before leaving, and unmount when the server/account/Workspace changes. All fields stay mounted in a scrolling form so off-screen errors cannot bypass validation. Background closes requests; foreground only reads. Ambiguous writes remain explicitly unconfirmed, are never replayed, and the draft refuses another Save until the user leaves and explicitly reloads the Agent. The detail reload reconciles the notice; foreground reads alone do not dismiss it. A phone-sized 2× system-text test covers the large form, not physical-device accessibility acceptance.

## ButterBoxes and Pi / Cursor Agents (#453)

A ButterBox is an agent VM that runs Pi and Cursor leaf Agents. The phone never connects to a Box and never runs anything on one by itself: every call goes to the Butter server, which holds the Box token, probes the Box and asks it for catalogs. A user run happens only when a person sends a chat message.

| Web operation | API | App entry | Tests |
| --- | --- | --- | --- |
| List / view boxes (name, URL, enabled, token set/updated) | ButterBoxService List/Get, `X-Workspace-ID` | Agents page → ButterBoxes → row | `box_controller_test`, `box_widget_test`, real `box_contract_test` |
| Register (name, base URL, enabled, optional token) / edit | Create / Update | Register ButterBox, Edit | same; `tool/contractserver/boxes_runtime_test.go` |
| Token: keep / replace / clear | Create's `token`; `SetButterBoxToken` (empty clears); Update never carries one | Edit keeps it; Replace access token and Clear access token are separate actions (a blank replacement is refused locally) | same |
| Test connection | `GetButterBoxStatus` — an unreachable box is data, not an error | Test connection (explicit; never on open) | same |
| Delete | `DeleteButterBox`; refused with `FailedPrecondition` naming the referencing Agents | Delete after a confirmation | same, against the real reference guard |
| Create / edit a Pi leaf: box, working directory, provider, model, thinking level, run limit | `AgentConfig.pi` via CreateAgent / UpdateAgent | Create Agent → type PI; Edit Agent | `box_leaf_draft_test`, `box_widget_test`, `box_contract_test` |
| Create / edit a Cursor leaf: box, working directory, model, mode, run limit | `AgentConfig.cursor` | type CURSOR | same |

**Run limit.** `max_run_seconds` is `optional`, and the three forms are different on the wire: *Server default* leaves it absent (the server applies 1800 seconds), *Unlimited* sends an explicit `0`, *Set seconds* sends a whole number from 1 to 2147483647. A stored explicit `0` shows as Unlimited and survives an unrelated edit; an invalid number blocks the save instead of becoming one of the others.

**Leaves have no Butter-side behavior.** Their instructions, tools, skills, memory and cards live on the Box, so the editor shows none of those fields, drops any left by an earlier type, and the server rejects them anyway (`InvalidArgument`, checked in `box_contract_test`). Instruction, MCP, Skill, Memory, Card Policy and children are therefore never written for a leaf. A model chosen on one box is cleared when the Agent is pointed at another; the working directory is kept as typed. Unknown fields of the stored Pi/Cursor message are preserved.

**Catalogs.** The status text of an unreachable Box is the server's raw probe error, which can carry whatever the Box or an intermediary returned, so the App only classifies it (token rejected, token unusable, capacity, timeout, cannot connect, otherwise "did not answer") and never displays it. Pi catalog failures (capacity, unreachable) and Cursor failures (`CURSOR_API_KEY` missing or invalid, a Box that does not serve CursorService, unreachable; the Cursor call may take up to 90 seconds) are mapped to messages that say what to do and always leave the model fields open for typing by hand. A disabled box is marked and cannot take a new binding; an Agent already bound to a missing or disabled box stays unchanged unless it is repointed.

**Session continuity (server contract, shown in the editor).** A conversation keeps one session on the Box per (conversation × Agent). Changing the Agent's ButterBox or working directory makes the next message start a fresh session; the old one is never moved or deleted on the Box. Model, provider, thinking level and mode apply to sessions created afterwards. This is the server's behavior and is covered by `boxes_runtime_test.go` and `box_contract_test.dart`.

**Evidence and its limits.** The Go contract test `TestEditingAnInstalledPresetKeepsItsHiddenCredentials` and `mcp_contract_test` run the keep seam through the production services, including a kept client secret completing a real PKCE flow and a replaced or cleared one not. `tool/contractserver/boxes.go` serves the production ButterBoxService, the production AgentService leaf validation, the real runner and the real `pibox` / `cursorbox` bridges. Only the Box itself is an in-process test double that serves the real generated Pi and Cursor Connect handlers (profiles at `/fake-box/ok`, `/capacity`, `/nokey`; a closed port is the unreachable one). It proves the transport, validation, token handling, catalog and run error mapping, continuity and repointing. It is **not** a production Box, a real Cursor/Pi model run, a TLS Box or a device run. Dart widget tests drive a controllable HTTP boundary (`test/support/box_server.dart`) for timing and failure shapes, and the real semantics are asserted in the contract tests.

Writes follow the app-wide rule: an ambiguous answer (a lost reply, a background close mid-write) is shown as unconfirmed, never repeated, and further writes stay off until a read reconciles it. Only a read that **began after** the write ended counts, so a slow read already in flight when a write was lost neither settles it nor replaces what the write left with an earlier snapshot; a read of one Box settles only a write aimed at that Box (a lost create is settled by the list). The same fence applies to a read that fails: once a write has stored newer state, an older read's failure (including a 401 it carries) is dropped instead of clearing the stored Box or marking the list failed, while a failure of the current read still reports and a current 401 still signs out. The token is held only in its dialog or field, sent once, cleared after sending, and never logged, displayed or read back (the server only reports that one is set).

## MCP servers and Remote Agents (#454)

Agents → **MCP servers** and **Remote Agents** are structured forms over MCPServerService, GlobalMCPService and RemoteAgentService. There is no JSON editor. Every call carries the Workspace header; a Workspace the person does not belong to answers *permission denied*, shown as such for reads and writes.

**Global presets are read and installed, never changed.** Creating, updating or deleting a global preset is global administration and is not in the App. Two server fixes came with this ticket: a non-admin used to receive preset header values (now redacted to `***`, `client_secret` empty), and installing a preset that does not exist answered `Internal` (now `NotFound`).

**Installed Workspace presets are editable, and keep what they hide.** An installed preset is stored with its real secrets but *returned* redacted, so saving that view back would overwrite the credentials with `***`; the App neither does that nor guesses a mask round-trip. Keeping is a protocol method of its own, `UpdateMCPServerKeepingCredentials` (`proto/agents/v1/agent_service.proto`, `docs/api.md`), usable by any client: the message plus the names of stored headers to keep (`keep_header_keys`) and whether to keep the stored OAuth client secret (`keep_oauth_client_secret`). `UpdateMCPServerRequest` is unchanged (`mcp_server` only, whole-object, as the Web console sends it). Extra fields on it would be a trap: a server that predates them ignores unknown fields and *deletes* the credentials the request meant to keep. A new method is safe the other way round, because an older server answers an unknown method with `404`, which the client reports as `unimplemented`, and stores nothing. So the App calls the plain `UpdateMCPServer` when nothing needs keeping (it works on every server), and calls the keep method only when something does; on `unimplemented` it records that the server cannot keep credentials, **blocks the save** with an explanation that the server must be upgraded (the edit form shows the notice and disables Save for such an edit) and never falls back to the plain request. The notice is reset when the page recovers. Kept credentials are named explicitly, never inferred from `***` or an empty value. The server refuses (`InvalidArgument`) a kept header that is not stored or is also given a value, and a kept secret under a different `client_id` or alongside a new one, forces the preset marker from the stored record so an edit can neither strip nor forge it, and always redacts the response. The App names a hidden row that is neither replaced nor removed, and a hidden client secret left on *Keep*; a replaced or removed credential is an explicit edit. Credentials the server never hides keep the old behaviour. *Old-server simulation:* the contract fixture's `/legacy` prefix registers `MCPServerService` without the keep method, so it answers that method with the plain `404` of an old server; the tests assert the App stops before any mutation (and `go test` asserts nothing changed). It simulates the missing method only; it is not a build of an older release, and no real older deployment was available here.

**Confirmations.** A save that discards stored credentials asks first, names the server and the target, and *Cancel* sends nothing: removing a header, clearing a client secret, changing the sign-in away from OAuth 2.0 when a client is registered (or away from Headers when headers would go), clearing an OpenCode password, and switching OpenCode to A2A. Renaming, rotating a secret or adding a header asks nothing. **Typed secrets do not outlive their submission:** when a save is sent, every typed password, header replacement and client secret is cleared from the form, whether the answer is *saved*, *denied* or *unconfirmed*; safe fields stay, a replacement stays chosen but empty, and sending again needs the value typed again. Nothing is replayed.

**MCP OAuth is not user-login OAuth.** It never touches `native_oauth.dart`'s sign-in handoff or session. Connect calls `StartMCPServerOAuth` with an empty `return_url`; the App opens the returned `authorization_url` in the system browser (`NativeOAuthPlatform.openBrowser`, injected) and shows *waiting*. The provider redirects to the server's public `/api/mcp/oauth/callback`, which exchanges the code and stores the token; nothing returns to the App. The App therefore reads the truth from `GetMCPServerOAuthStatus`: it takes a baseline before starting and calls the server connected only when `connected` is true with a `connected_at` different from that baseline (so an earlier connection is never mistaken for this one). **Foreground watch.** While a flow is waiting and the app is in the foreground, the controller reads the status every 5 seconds (`mcpOAuthPollInterval`) and ends the wait at the flow's 10-minute deadline (`mcpOAuthFlowTtl`); the **Check** button reads once more on demand. Properties, each held by `mcp_oauth_watch_test` on a hand-moved clock: the watch only reads and never replays Start or any write; it has one read in flight at a time (the next is armed when the previous one finishes, so a slow read is not stacked upon); the deadline is its own timer, so it ends the wait even when status reads fail or hang, drops any answer still on its way, and then makes one last read, so a connection finished in the last moment is reported as connected and one that was not is reported as *timed out* ("expired"; a failed last read does not replace that); a finished, stopped, disconnected, deleted, replaced or disposed flow cancels its timers and a stale answer is dropped by the flow's sequence number; a new Connect replaces the earlier watch, never doubles it. Suspend cancels every timer (nothing runs in the background); `recover()` ends the wait at once if the deadline has passed, whatever the read does, otherwise it reads once and watches again. **Stop waiting** is local — the server has no cancel, so the link stays valid; a connection that then finishes is still shown as connected on the next read, and a flow that timed out is likewise settled from server state. The server keeps no record of a failed flow, so a provider denial or a failed token exchange is visible only as *not connected*, and the App says so instead of inventing a reason. A start whose answer was lost when the app was backgrounded becomes *failed, start again* (the start is a write and is not replayed). Opening the authorization link cannot be verified from the App: the launcher only says whether the system accepted the URL. Disconnect is a fenced write.

*Flow fencing.* Every flow carries a sequence number, and every continuation re-checks it and that the server object still exists after each await: a Start that answers after a newer disconnect, edit, delete, stop-waiting or another Connect never opens the browser and never restores authorization; a stale status read cannot overwrite a newer state. The *launching* state is recorded before the system browser is asked to open the link, so a suspension while the launcher is still pending reloads the real authorization instead of dropping it. A launcher that refuses or throws is reported as a failure to open the browser. **Limitation:** a link the browser already opened cannot be revoked by the App, and the server has no cancel, so the provider page may still be completed after the App has moved on; the next status read then shows the truth.

**Probe text is untrusted.** `MCPServerStatus.detail`, `ListMCPToolsResponse.errors` and `RemoteAgentStatus.detail` carry whatever the remote endpoint or an intermediary returned, so the App only classifies them (rejected credentials, authorization needed, cannot connect, timed out, HTTP status, otherwise "did not answer") and never displays them. URLs are validated as absolute http(s) before saving, including OAuth endpoints and `resource`; the server checks again.

**Preservation and writes.** A draft is a deep copy of the whole generated message, so unknown fields, `metadata` and `workspace_id` survive an edit, and optional fields stay absent unless changed. A Remote Agent keeps `daemon_runtime_id` / `acp_runtime` only for the DAEMON protocol (#455 added it to the draft; the protocol's own section is below). Writes follow the app-wide rule: an ambiguous answer is *unconfirmed*, never replayed, and further writes stay off until a read **that began after the write and covers the same object** reconciles it (scopes `config` and `oauth` are separate). Suspend closes requests and drops the loaded servers and credentials; foreground re-reads the list and the open item.

**Not in this ticket.** The Daemon protocol was ticket #455 (see its section). The MCP and Remote Agent reference editors inside the Agent form, and Skills, stay with the Agent tickets. Global preset administration is out of scope.

**Server gaps recorded.** (1) Non-admin preset listing leaked header values — fixed. (2) Installing a missing preset returned `Internal` — fixed. (3) Probe `detail` strings are raw. (4) No failed-flow record or server-side OAuth cancel. (5) Editing an installed preset through its redacted view would corrupt credentials — solved with the explicit keep fields above (no mask round-trip). (6) Unknown-field storage was verified with the in-memory repositories only, not Mongo.

**Evidence and its limits.** `tool/contractserver/mcp.go` serves the production services and the production OAuth callback handler (`internal/handler/http/mcp_oauth.go`) on in-memory repositories. The MCP server, the authorization server (PKCE S256, single-use codes, `deny` / `tokenfail` scopes), A2A and OpenCode endpoints are in-process test doubles, and the "browser" in the Dart contract test follows the redirects with `dart:io`. This is **not** a real identity provider, a real system-browser round trip, a Mongo-backed run or a device run.

## Daemon execution (#455)

Agents → **Daemon execution** manages the Workspace's daemon runtimes, the workers connected to them, worker tokens, tasks in flight and server diagnostics, over `DaemonService` and the list/revoke half of `APITokenService`. **No worker is started on the phone**: a worker is `cmd/butter-daemon` on your own machine, and the App only prepares its runtime and token and watches it. No global-administration entry was added. Every call carries the Workspace header; a Workspace the person does not belong to answers *permission denied*.

| Operation | API | App entry | Tests |
| --- | --- | --- | --- |
| List / view / create / edit / delete runtimes, with name, description and labels (key/value rows) | `ListDaemonRuntimes`, `GetDaemonRuntime`, Create, Update, Delete | Daemon execution → row, Add runtime, Edit, Delete | `daemon_draft_test`, `daemon_controller_test`, `daemon_widget_test`, real `daemon_contract_test` |
| Is a worker online, its version, OS, executors | `ListDaemons` (a runtime that is not listed is offline) | runtime row and detail | same |
| Mint a worker token (name and optional expiry in hours, secret shown once) | `CreateDaemonRuntimeToken` (`ttl` only when an expiry was chosen) | runtime detail → Create worker token | same, and a real expiry/no-expiry contract |
| List / revoke worker tokens | `ListAPITokens` (kept to `API_TOKEN_KIND_DAEMON`), `RevokeAPIToken` (owner/admin) | runtime detail → tokens | same, as owner (`daemon`) and as a plain member (`mcp`) |
| Bind a Remote Agent to a runtime and executor | `CreateRemoteAgent` / `UpdateRemoteAgent` with protocol DAEMON | Remote Agents → Add / Edit → **Daemon** | `remote_agent_test`, `remote_agent_widget_test`, `remote_agent_daemon_test`, contract |
| Reference status | `ListDaemonRuntimes`, `ListDaemons`, `GetRemoteAgentStatus` | Remote Agent row and detail | same |
| Tasks in flight: step, progress, elapsed | `ListDaemonTasks` (read again every 5 s while the page is open and foreground, one read at a time: the next is armed when the last has ended, and a refresh joins a read in flight) | Daemon execution → Tasks → row | `daemon_controller_test`, `daemon_widget_test`, contract |
| Cancel | `CancelDaemonTask` (with the task's runtime) | Tasks → Cancel, confirmed | same |
| Server diagnostics | `GetBridgeDiagnostics` | Daemon execution → Diagnostics | same |

**Two kinds of token, never mixed.** The App never calls `CreateAPIToken`. A worker token comes only from `CreateDaemonRuntimeToken` (kind DAEMON, scope `daemon:connect`, bound to one runtime in one Workspace) and is not accepted by the HTTP API; a personal API token is not accepted by the worker transport. The inventory drops every token that is not DAEMON the moment it arrives, so a user token never reaches App state or the screen. The runtime detail says a worker token is not a personal API token.

**The one-time secret.** It lives on one object (`DaemonController.minted`) and is shown only on the runtime detail, with **Copy** (the clipboard is outside the App's control, and the screen says so) and **I have saved it**. It is wiped (the field is nulled and the object dropped) on dismissal, on suspend (the app going to the background), when the runtime detail is left (back, delete) and when the context is disposed (sign-out, server or Workspace change); reopening the runtime never shows it. While it is shown, Edit and Delete are off, so no other screen is opened over it. A mint still in flight when the screen is left is fenced: its reply is not kept (the token exists, so the write is marked unconfirmed and the message says its secret was discarded and the token should be revoked), and nothing is minted again. A second token cannot be minted while one is on screen. The token's name and an optional expiry in hours, as in the Web dashboard, are chosen in the dialog. The expiry is any positive decimal number of hours (`1`, `12`, `0.5`, `720`; `parseExpiryHours`) and is sent as the request's `ttl` Duration in whole seconds plus nanoseconds, so sub-day and fractional-hour lifetimes arrive exactly (the real-server contract mints 30-minute, 1-hour and 12-hour tokens and checks their `expires_at`). The only upper bound is what the server can represent (2,562,047 hours, its `time.Duration`; a longer one would be clamped without a word, so it is refused). An empty expiry is the one way to send no `ttl`, so the token lasts until revoked, and the dialog says so. Zero, negative, `NaN`, `Infinity`, exponents, words and separators are refused before any request and never become a token without an expiry; the controller and the API client also refuse a non-positive `Duration`, because the server reads a zero `ttl` as "never expires". **A lost mint reply is never repeated:** minting stores another token on every call, so the write is *unconfirmed*, the screen says a token may exist whose secret can never be shown, and every further write stays off until a token-list read that began afterwards. The person then revokes what they do not recognise and mints once more on purpose. A mint that was in flight when the app went to the background is the same. The App cannot tell which listed token a lost mint made.

**Cancel is delivery, never a stop.** `CancelDaemonTask` success means the server handed the request to the worker; the worker reports its own end. The App says *Cancel delivered … the task is still running until the worker reports back*, keeps the task in the list, and never shows "cancelled". Outcomes are told apart: delivered; *no connected worker runs this task* (not found: nothing delivered); *the server could not hand it to the worker* (internal: the worker may just have gone, the task may still run); refused (no access); and *lost answer* (may or may not have been delivered). A repeat is harmless, so none of them locks the button except one in flight. A task that leaves the list is shown under *Left the list* with "outcome not reported": the server lists tasks in flight only and keeps no history, so the App neither claims cancelled, completed nor failed. A cancel that was in flight when the app went to the background is reported as not confirmed.

**Reference problems.** A Daemon Remote Agent names a runtime (picked from this Workspace's runtimes; the picker keeps a dangling stored ID visible as "not in this Workspace" so it can be replaced, and Save refuses it before any request) and an executor (`opencode` or `codex`, the only two the server runs). The row and detail say when the runtime does not exist (the server does not guard runtime deletion) or when the connected worker does not offer the executor. Nothing is claimed before the runtimes were read. Deleting a runtime first reads which Remote Agents use it and lists them in the confirmation (or says the check failed); its tokens stay listed and unrevoked.

**Preservation.** Runtime edits start from the stored copy (creator, Workspace and unknown fields ride along). Labels are edited as key/value rows: an untouched set is left exactly as stored, a touched one replaces the map whole, an empty row is ignored, and a blank or repeated key is refused before any request; the Remote Agent draft keeps unrelated fields when the protocol changes and asks before discarding anything stored (OpenCode credentials, A2A URL). Strings a worker reports about itself (name, version, OS, executors, labels, step) are shown as plain text, bounded; the server-captured peer address is not shown. Probe text stays untrusted: the reason is classified, never displayed.

**Fixes made for this ticket.** (1) `internal/agent.resolveRemoteAgents` resolved Remote Agent IDs in one flat registry, so two Workspaces using the same Remote Agent ID got each other's agent (and its worker) at run time; it now resolves among the host Agent's own Workspace (`TestSameRemoteAgentIDInTwoWorkspacesDispatchesToItsOwnWorker`). (2) A log line said a cancel was "sent", which is the delivery claim above; it now says "delivered". (3) `resolveMCPServers` had the same flat lookup, so two Workspaces with the same MCP server ID could resolve to each other's endpoint and headers; it too resolves only among the host Agent's Workspace (`internal/agent/resolve_workspace_test.go`, which also covers the Remote Agent lookup).

**Server gaps recorded.** `ListDaemonTasks` and the in-memory task state hold in-flight tasks only, so there is no task history or terminal status for the App to show. `GetBridgeDiagnostics` is server-wide, not Workspace-checked, and not about a worker. `DeleteDaemonRuntime` has no reference guard and does not revoke tokens. `CreateDaemonRuntimeToken` has no role check while revocation needs owner/admin, so a plain member can mint a token they cannot revoke. The runner's Remote Agent and MCP registries are still one flat list across Workspaces; since the fixes a host Agent resolves only its own Workspace's entries, but IDs in other Workspaces still share that list.

**Evidence and its limits.** `tool/contractserver/daemon.go` serves the production `DaemonService`, the production worker poll transport, `APITokenService` (list and revoke), `RemoteAgentService`, the registry and the production runner with its daemon Bridge, on in-memory repositories. The **only** double is the worker: a deterministic fake that speaks the real Register / Poll / ReportTaskUpdate / Unregister protocol with the token the App minted (`cooperative` reports CANCELLED on a cancel, `stubborn` records it and keeps working), driven over a loopback control API. `go test ./mobile/tool/contractserver` and `daemon_contract_test` (at the root and under `/butter`) assert dispatch, status and cancel over that path and tenant isolation (a peer Workspace sees no foreign task, cannot cancel it, cannot read the runtime; the same runtime ID in two Workspaces is two runtimes). This is **not** a real opencode or codex run, a real `cmd/butter-daemon`, a Mongo/Redis-backed run, a TLS deployment or a device run. Dart widget tests drive a controllable HTTP boundary (`test/support/daemon_server.dart`) for lost, late and refused replies.

Delivery rules: the SSE parser accepts arbitrary UTF-8 chunking, LF/CRLF/CR, multi-line `data:`, comments (heartbeats) and a bounded event size. A POST is **never** retried. A request that was refused (400 `thread_unbound`, 403, 404, 409, 413, 503) or never connected returns the turn to the composer; one whose outcome is unknown shows an `unconfirmed` notice and is not resent. `test/chat_contract_test.dart` (via `tool/contract.sh`) drives `ClientContext` against the production AG-UI handler, runner, `SessionServiceServer` and detached-run machinery in `tool/contractserver/chat.go`; only the model (a loopback OpenAI-compatible echo) and persistence are replaced. It covers a detached two-send conversation and history in a fresh session, Markdown, an image round trip, server-normalized rename, Workspace isolation, and the `thread_unbound` / `run_exists` refusals, at root and `/butter`. `contract.sh` runs `flutter test` without `--no-pub`; on a Flutter SDK other than the pinned one it re-resolves `pubspec.lock`, so restore it with `git checkout` before committing.

Scope notes: tool-role results only answer client-declared frontend tools, and this App declares none, so a run request carries exactly one user message. An Agent shows its name and an initial, not its configured avatar image, so chat fetches no remote image.

Not provided yet (labelled in the UI): reconnecting to a live run after leaving or a dropped stream, **Stop**, and A2UI forms/cards (an Interrupt shows a "waiting for input" notice only). Workflow Human Input cannot be answered in the App.

## File spaces and Agent associations (#456)

Workspace → **File spaces** manages `AgentFileService`: spaces, the text files in them, their versions and search. The Agent editor (LLM, Loop, Sequential, Parallel and Workflow Agents; Pi and Cursor leaves are unchanged) selects the existing MCP servers, Remote Agents, file spaces (mounts) and Skills an Agent references. Skill creation, `SKILL.md` editing and Skill Resource management stay in Web: the Skill list is read for selection only. File content travels as the UTF-8 text of `WriteAgentFile` / `GetAgentFile`, never through the avatar upload.

| Operation | API | App entry | Tests |
| --- | --- | --- | --- |
| List / view / create / edit / delete a space | `ListAgentFileSpaces`, `GetAgentFileSpace`, `CreateAgentFileSpace`, `UpdateAgentFileSpace` (whole record; the edit starts from a fresh read), `DeleteAgentFileSpace` (confirmation names the space, the number of files it holds and the Agents that mount it, or says the check failed) | File spaces → row, Add, Edit, Delete | `file_controller_test`, `file_widget_test`, real `files_contract_test` |

| Open / create / edit / save a file | `GetAgentFile`, `WriteAgentFile` (UTF-8 text, content type and metadata carried over because a write replaces them); path normalized as the server does (trim, leading `/`, clean; empty and `/` refused) and shown before saving | space → file → Edit, New file | `file_rules_test`, `file_controller_test`, `file_widget_test`, contract (a table of paths against the real server) |
| Versions | `GetAgentFile(version)`; older versions show text and content type only (metadata is not versioned); **Restore** writes the old text as a new latest version and says so | file → Older / Newer / Jump | same |

| Mount file spaces | `ListAgentFileSpaces`, saved as `AgentConfig.file_mounts` | Agent editor → File mounts (space, virtual path, permission) | `agent_association_test`, contract |

**What the server does, and so what the App says.** There is no compare-and-swap and no history-list RPC: every write makes a new version, so a concurrent edit cannot be refused by the server. The App reads the file just before saving and refuses a save over a version it did not open (`exists`, `changed`, `deleted`), and the dialog says this narrows the window and does not close it; only an explicit **Overwrite** replaces it. Version numbers come from the latest read; the App never invents a history listing, and versions are reached by number. The size limit is the server's (256 KiB by default, counted in UTF-8 bytes; the App reads it from the refusal text and shows digits only), a file over 1 MiB is not opened on the phone, and content is text only. A write whose reply is lost is never repeated: it is *unconfirmed* until a read of the same file settles it (**Check whether it was saved**). A read that began before a write, or about another object, cannot settle it. Spaces never cross Workspaces; a Workspace the person does not belong to answers *permission denied*; `FailedPrecondition` "agent file repository not available" is shown as storage not configured.

**Associations by Agent type** (what the runtime uses, proven by `TestSavedAssociationsDecideWhatARealRunCanDo`):

| Agent type | MCP servers | Remote Agents | File mounts | Skills |
| --- | --- | --- | --- | --- |
| LLM | yes | yes | yes | yes |
| Loop / Sequential / Parallel | ignored: retained, remove only | yes | ignored: retained, remove only | ignored: retained, remove only |
| Workflow | ignored: retained, remove only | ignored: retained, remove only | ignored: retained, remove only | ignored: retained, remove only |
| Pi / Cursor leaf | not offered (the server refuses them) | not offered | not offered | not offered |

On a new Agent the draft keeps what was chosen if the type is switched back, but `buildForCreate` does not send associations the final type ignores. On an existing Agent, ignored legacy entries are shown with removal only, because a reference to a missing server still makes the server refuse the save.

**Mounts.** Each mount has a virtual path, a permission and its space. A new mount defaults to a slug of the space name and an explicit `READ`. Paths are normalized as the runtime does (empty → `/`); **two mounts that normalize to the same path are blocked in the editor**, because the runtime silently drops the later one. The longest path wins. The runtime offers the file tools whatever the permission and refuses a write or delete the permission does not allow when it runs (the editor says so, and names the space when it grants write or delete). `UNSPECIFIED` behaves as read-only. A permission the App does not know (a newer server) and any unknown field on a mount are kept byte for byte until the person picks a permission. A mount of a space that is not in the Workspace is flagged: the server accepts it and every file call through it fails.

**Honest lists.** Each association list loads on its own. A refused or failed list (permission denied, unavailable) never blocks editing: the current selection stays, the editor says why nothing can be added, and server text is never shown. A selected reference missing from a loaded list stays selected and flagged until removed. A save refused because a reference no longer resolves (the server rebuilds the runtime and rolls the save back, answering `internal`) reads *Nothing was saved: an MCP server / a Remote Agent this Agent references no longer exists*; it is not retried.

**Evidence and its limits.** `tool/contractserver/files.go` serves the production `AgentFileService` (in-memory repositories) and wires the production runner with the file store, the Skill repository and the MCP and Remote Agent registries; `go test ./mobile/tool/contractserver` (`files_runtime_test.go`) exercises the service semantics and real runner turns, and `files_contract_test` (root and `/butter`) saves an Agent from the App, reads it back, then runs it through the production AG-UI route: the mount's tool reads the stored content, a `READ` mount refuses a write and leaves the space unchanged, the saved MCP server's tool runs, the Skill is listed, and raising the permission and saving lets the next run write (a new version) but not delete. The **doubles** are the scripted OpenAI-compatible model (`tools?` and `tool:<name> <json>` commands) and the in-process MCP server; storage is in memory, not S3 or Mongo, and no real model provider or device was involved. Dart widget tests use a controllable HTTP boundary (`test/support/file_server.dart`) for late, refused and lost replies.

## Tests and device acceptance

Unit/controller/widget tests use public application interfaces with fake **external** HTTP/OS-storage boundaries. They cover first setup, persistence, real request headers, permission/empty/error/pagination UI, admin without global navigation, expiry, relogin/server/Workspace races, slow credential writes, vault failure and generated-field retention. The separate Go contract fixture is a real-service HTTP integration test.

```sh
# Terminal 1, repo root:
go run ./mobile/tool/contractserver -addr 127.0.0.1:8080
# Terminal 2, Android emulator/device attached by adb:
adb reverse tcp:8080 tcp:8080
cd mobile
flutter test integration_test/login_test.dart -d <device-id> \
  --dart-define=BUTTER_TEST_SERVER=http://127.0.0.1:8080 \

# Prefer a trusted HTTPS tunnel if simulator ATS rejects local HTTP.
```

HTTP is accepted only with an explicit `BUTTER_ALLOW_HTTP=true` **debug** build; release code never permits it. Android's debug-only manifest supports that development mode; iOS has no global ATS exception or TLS bypass. Do not expose the fixture publicly. The native test exercises the actual platform vault, UI forms, real HTTP services, restoration via a fresh context and logout. It deletes development credentials; do not point it at a real user's installation. For ordinary manual login, enter credentials in the App, not build flags.

Cold Android builds use a 2 GiB Gradle heap and a 512 MiB Metaspace cap, one worker and in-process project Kotlin compilation. Allow additional RAM for Flutter, the SDK's compiler and the OS. Earlier local verification built a warm-cache arm64 debug APK (`flutter build apk --debug --target-platform android-arm64 --no-pub`) under a 2 GiB container limit; this does **not** establish that a clean multi-ABI build fits that limit. Production-handler contracts (including path prefixes), analysis and generation drift checks also passed.

This Linux environment cannot run Xcode/iOS builds or native device acceptance. CI provides a macOS unsigned simulator build check, but **an unexecuted workflow is not a passing iOS build**. Android/iOS physical-device vault, backup/restore, app restart and accessibility checks remain required before release. Do not mark those acceptance items complete based on plugin mocks or this README.
